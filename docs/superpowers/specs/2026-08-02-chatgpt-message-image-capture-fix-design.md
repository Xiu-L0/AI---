# ChatGPT 消息图片可靠采集修复设计

- 日期：2026-08-02
- 范围：Recall AI Milestone A
- 状态：用户已批准

## 1. 问题与验收证据

真实 Chrome 第 17 次验收在 ChatGPT 完整会话中发送了一张合成 PNG。ChatGPT 页面显示该图片并能识别其内容，但 Recall AI 扩展返回“完整采集成功”、6 条消息和 0 个附件。Web 端同一 SourceItem 新增版本 3，保存了 6 条文字消息，没有附件或缺失元素，异常计数仍为 0。

页面检查确认图片位于用户消息容器内，结构为 `button > img`，具有文件名形式的 `alt`、有效的 `https://chatgpt.com/backend-api/estuary/content...` 地址以及正数宽高。当前提取器用通用规则 `button img` 排除所有按钮内图片，因此在完整性检查之前丢弃了真实附件缩略图。

## 2. 目标与非目标

目标：

- 识别 ChatGPT 消息容器内可保存的用户上传图片，包括位于按钮内的附件缩略图。
- 继续排除头像、反馈图标、隐藏图片和消息容器外的界面装饰。
- 图片可读取时，将其作为附件保存并由 durable receipt 报告真实附件数。
- 图片存在但无法读取时，返回 `partial`，列出对应消息中的缺失图片，并提供既有恢复动作。
- 禁止在图片既未保存、也未列为缺失时返回 `complete`。

非目标：

- 不增加对新平台或新文件类型的支持。
- 不增加 OCR、AI 图片理解或 Milestone B 功能。
- 不改变服务器两阶段保存协议、附件限制、RLS 或敏感级别规则。
- 不追溯修改已经持久化的错误版本；修复后通过新版本复测证明行为正确。

## 3. 方案选择

采用精确识别消息图片的方案：移除“所有按钮内图片均排除”的宽泛规则，保留现有头像、反馈、图标、隐藏状态和消息归属过滤。图片必须同时满足：

1. 位于支持的 ChatGPT 消息容器内部；
2. 最近的消息容器就是当前正在提取的容器；
3. 不命中明确的头像、反馈、图标、展示用途或隐藏标记；
4. 具有可检查的图片节点；其来源地址是否可读由现有完整性与附件准备流程继续判断。

不采用“采集所有按钮图片”，因为它会增加误采集界面装饰的风险；不采用“所有含图会话一律 partial”，因为它会放弃当前已有的真实附件上传能力。

## 4. 数据流与错误处理

数据流保持不变：

1. 内容脚本从 ChatGPT 消息容器提取文字、消息标识和图片元数据。
2. 范围选择逻辑只保留属于完整会话或当前问答的图片；选中文字仍不附带图片。
3. 可读的 `https:` 或受限 `data:image/` 来源进入待准备附件列表。
4. Capture Runner 下载图片、校验来源、MIME、大小、签名和哈希，并持久保存 Blob。
5. 下载或校验失败时，把该图片转成具体的 `missingElements`，将采集降级为 `partial`。
6. 只有附件上传完成且服务器 durable finalize 返回 receipt 后，界面才显示完整或部分采集结果。

服务器拒绝、网络失败和本地 Blob 丢失继续使用现有 Outbox 与重试逻辑，不创建合成成功回执。

## 5. 测试设计

新增回归测试使用与真实页面一致的 `button > img` 结构，并断言：

- 消息中的附件缩略图会被提取，来源、文件名提示、尺寸和消息归属正确；
- 明确的头像、反馈、图标和隐藏按钮图片仍被排除；
- 可读图片进入 pending attachment，而不是被静默忽略；
- 不可读图片产生 `partial` 和明确缺失项；
- 原有完整会话、当前问答、选中文字和去重测试继续通过。

验证顺序：聚焦提取与完整性测试、全部扩展单元测试、扩展类型检查、Manifest V3 正式构建。重新加载正式构建后，在同一真实 ChatGPT 会话复测：合格结果只能是附件数 1 的完整采集，或列出缺图的部分采集；附件数 0 的完整采集必须失败。

## 6. 完成标准

- 自动化回归测试全部通过。
- 正式扩展成功重新构建。
- 真实 Chrome 复测不再出现“0 个附件但完整成功”。
- Web 端新版本显示附件 1；若外部图片地址无法由扩展读取，则显示 `partial` 和具体缺失图片。
- 第 17 次原始失败样本保留在验收记录中，另记录修复后的复测结果，不从正式分母移除。
