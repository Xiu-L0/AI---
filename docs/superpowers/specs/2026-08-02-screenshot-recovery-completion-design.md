# Recall AI 截图恢复完成状态修复设计

- 日期：2026-08-02
- 范围：Milestone A 的 ChatGPT 部分采集截图兜底
- 状态：用户已选择方案 A

## 问题

ChatGPT 消息图片因受保护资源返回 HTTP 403 时，扩展能够诚实返回部分采集并提供“补充截图”。但当前截图恢复草稿继承原部分采集的 `missingElements`、`completeness` 和历史恢复附件，导致：

- 截图已成功上传并形成新版本，弹窗仍显示“部分内容未采集”；
- Web 异常始终存在；
- 用户无法判断点击是否成功，可能重复点击；
- 每次重复操作都会继承此前截图并继续追加，形成多版本和重复附件。

真实验收已证明截图、私有附件上传和持久化本身正常；缺陷位于恢复草稿和完成状态的表达。

## 目标行为

一次“补充截图”操作是对已确认 partial receipt 的人工兜底。截图成功获得服务器 durable receipt 后：

1. 新恢复版本使用与原记录相同的 ChatGPT 来源、会话引用、消息和敏感级别。
2. 新恢复版本只包含本次生成的一张 `image/png` 截图，不继承先前恢复版本中的截图附件。
3. 由该截图兜底的原缺失项从新版本中移除。
4. 新恢复版本以 `complete` 完成，扩展显示“完整采集成功”及服务器返回的真实消息和附件数量。
5. 原 partial 记录保留为历史证据，并由成功恢复记录标记为已解决；扩展角标和 Web 异常不再把它计为未解决。
6. 截图、上传或 finalize 失败时，不创建合成成功回执；原 partial receipt 保持未解决，并展示实际错误或重试状态。

## 交互与并发保护

- 用户点击“补充截图”后，按钮立即进入“正在补充…”并禁用，直到操作完成或失败。
- 成功后当前弹窗切换到新的 complete receipt，不再显示“补充截图”。
- 同一 partial 项已有未完成或已完成的截图恢复子项时，不允许再次创建平行恢复尝试；应返回现有子项或明确拒绝重复操作。
- 该保护以 Outbox 数据为准，不能只依赖 React 按钮状态，避免关闭并重新打开弹窗后的重复提交。

## 数据边界

- 不删除、不回滚、不改写验收期间已经形成的版本 5–11。
- 不修改原 partial receipt 的内容；只通过恢复关系记录其已解决状态。
- 不扩大 Milestone A：不尝试绕过 ChatGPT 图片授权，不新增 OCR、图片理解或 AI 调用。
- 截图仍使用既有 `activeTab` 能力、10 MiB 单附件限制、50 个附件和 100 MiB 总量限制。

## 实现边界

主要修改限于扩展截图恢复编排及其测试：

- `screenshotRecoveryDraft` 构造完整、单截图的恢复草稿；
- `addScreenshotRecovery` 在创建前检查既有恢复子项；
- 弹窗继续以服务器 receipt 为唯一成功依据，不合成成功状态；
- 如现有 Web 恢复关系已能在 complete receipt 后清除异常，则不修改 Web 或数据库；只有测试证明其不满足上述目标时才做最小修正。

## 验证

自动测试至少覆盖：

1. partial + 一次截图成功后返回 complete，缺失项为空，附件正好一张；
2. 原 partial receipt 保持不变但被标记已解决；
3. 成功后未解决计数归零；
4. 连续或重新打开弹窗后重复点击不会创建第二个恢复子项；
5. 截图失败、上传失败和 finalize 失败仍保持诚实失败，不丢失原 partial；
6. 正式扩展类型检查、测试、构建、Manifest 与 secret 检查继续通过。

真实 Chrome 复测要求：同一含图会话产生一个新的完整版本，保存六条消息和一张 PNG 截图，扩展异常数及 Web 异常数均归零。
